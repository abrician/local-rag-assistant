# Учебное руководство по Local RAG Assistant

Это руководство поможет разобраться в устройстве проекта и объяснить его решения на собеседовании. Полезно читать его вместе с исходным кодом и запускать небольшие эксперименты самостоятельно.

## 1. Общая архитектура

RAG (Retrieval-Augmented Generation) соединяет поиск по документам и генерацию текста. Сначала **retrieval** находит подходящие фрагменты, затем (если включено) **generation** передаёт их языковой модели как контекст и просит сформулировать ответ. Поиск выбирает уже существующий текст; генератор создаёт новый текст и может ошибаться.

Документы — исходные файлы. Фрагменты (chunks) — части документов, с которыми удобнее работать по отдельности. Индекс — подготовленное числовое представление фрагментов, позволяющее быстро сравнивать их с запросом.

Путь запроса таков: клиент отправляет JSON в `/ask`; API проверяет значения; выбранный поиск ранжирует фрагменты; при `use_llm=true` контекст отправляется Ollama; API возвращает найденные фрагменты и, если доступно, ответ модели. Для embeddings модель и индекс создаются при первом таком запросе; если модель ещё не находится в локальном кеше, её файлы сначала скачиваются. TF-IDF работает отдельно.

## 2. Загрузка документов — `src/data/loader.py`

`Path` из стандартного `pathlib` представляет путь к файлу независимо от ручной склейки строк. `load_documents` рекурсивно ищет `.txt`, сортирует пути для стабильного порядка и читает UTF-8. В результате каждый документ представлен словарём с текстом, именем, категорией и относительным источником.

`clean_text` нормализует окончания строк Windows и Unix и убирает только крайние переводы строк. Она сохраняет внутренние пустые строки и отступы. Это важно для Python: строка `    return value` имеет отступ, являющийся частью синтаксиса, а пустые строки помогают понимать структуру примера.

**Chunking** делит длинный текст на части. Для TF-IDF `split_into_chunks` считает группы непробельных символов (слова) и вырезает диапазоны из исходной строки, не собирая текст заново. Параметры по умолчанию — 200 слов и overlap 50 слов. **Overlap** — повтор части предыдущего фрагмента в следующем: так контекст у границы не пропадает.

Слова и токены — разные единицы. Токенизатор модели может разбивать слово на несколько токенов или учитывать знаки пунктуации по-своему. Поэтому размер окна в словах не гарантирует, что фрагмент поместится в embedding-модель. Для embeddings `split_into_token_chunks` использует быстрый токенизатор с символьными смещениями, учитывает специальные токены и проверяет итоговую длину. `model_chunk_options` выбирает окно до лимита модели; перекрытие обычно составляет до 32 токенов.

Историческая проблема была в том, что длинные фрагменты подавались модели, у которой лимит входа равен 256 токенам. Модель обрезала хвост, поэтому embedding не представлял весь фрагмент. Теперь чанки ограничиваются реальными токенами конкретного токенизатора, а пересечение окон сохраняет непрерывность текста.

## 3. TF-IDF — `src/models/tfidf_search.py`

TF-IDF превращает тексты в разреженные числовые векторы. **TF (term frequency)** отражает, как часто термин встречается в тексте. **IDF (inverse document frequency)** уменьшает вес слов, часто встречающихся во многих документах, и увеличивает вес более характерных терминов. Векторизатор проекта использует однословные и двухсловные признаки (`ngram_range=(1, 2)`) и суб-линейное масштабирование частоты.

Например, пусть есть документы «Python использует списки» и «Python использует словари», а запрос — «списки Python». Слово «Python» встречается в обоих, поэтому оно менее различительно; «списки» лучше указывает на первый документ. После векторизации `cosine_similarity` сравнивает направление вектора запроса и каждого фрагмента. Чем ближе направления, тем выше оценка. Это учебная иллюстрация принципа: точные веса в этом примере зависят также от настроек векторизатора.

На небольшом тематическом корпусе TF-IDF может быть сильным: одинаковые термины и названия методов дают полезные совпадения, а построение индекса быстрое. Но он плохо понимает перефразировки и смысловые отношения, если слова различаются. Также обычный word-level векторизатор чувствителен к языковым формам и формулировкам.

`fit` строит векторизатор и индекс. `search` возвращает результаты по убыванию косинусной близости, пропускает нулевые совпадения и проверяет `top_k`.

## 4. Embeddings — `src/models/embedding_search.py`

Embedding — плотный числовой вектор, который модель строит для текста. Sentence Transformers кодирует запросы и фрагменты одной моделью; тексты со схожим смыслом могут иметь похожие векторы, даже если слова не полностью совпадают. В коде затем применяется cosine similarity.

**Токенизатор** переводит текст в последовательность токенов, понятных модели. У каждой модели свои правила и максимальная длина. Специальные токены, например маркеры начала и конца последовательности, тоже занимают место.

Раньше chunking считался по словам и мог создавать слишком длинные куски. Модель `all-MiniLM-L6-v2` принимает до 256 токенов, включая специальные; длинный текст обрезался. Исправленная загрузка получает токенизатор модели и его лимит, строит окно по токенам, сохраняет перекрытие и исходные символы. Поэтому длина учитывается не приблизительно, а по фактическому разбиению токенизатора.

Преимущество embeddings — поиск смысловой близости и перефразировок. Ограничения — стоимость загрузки модели, более медленный запуск/поиск и зависимость результата от обучающих данных и языка. На небольшом контрольном наборе сложная модель не обязана превзойти лексический baseline.

## 5. Ollama и Qwen — `src/models/llm_generator.py`

Ollama — локальный сервис, который запускает языковые модели и предоставляет HTTP API. Qwen — семейство языковых моделей; проект по умолчанию передаёт Ollama имя `qwen2.5:1.5b`, если в окружении задан `OLLAMA_MODEL`, используется его значение. При прямом вызове `generate_answer` имя можно также передать аргументом `model`.

`generate_answer` склеивает найденные фрагменты в контекст, добавляет инструкцию отвечать по предоставленным отрывкам и включает вопрос. Затем отправляет запрос на `/api/generate` с `stream=false`. При недоступности сервера, ошибке HTTP или некорректном JSON возвращается `None`. Если сервер отвечает успешно, но поле `response` отсутствует, функция возвращает пустую строку.

Контекст помогает модели опираться на корпус, но не гарантирует правильность. Модель может неверно понять отрывок, пропустить важную деталь или уверенно выдумать вывод. Retrieval и generation — отдельные этапы: точный поиск не доказывает, что текст ответа точен.

## 6. FastAPI — `src/service/api.py`

API — способ, которым одна программа просит другую выполнить действие. HTTP задаёт формат таких запросов и ответов. `GET` обычно читает состояние; `POST` передаёт данные для обработки. В проекте `GET /health` показывает состояние корпуса и доступность Ollama, а `POST /ask` принимает запрос и возвращает найденные фрагменты.

JSON — текстовый формат объектов и списков, часто используемый веб-сервисами. Pydantic-модели `AskRequest`, `SearchResult` и `AskResponse` описывают поля и типы. FastAPI проверяет входные данные и формирует документацию API. `top_k` на уровне приложения должен быть от 1 до 10; `method` — `tfidf` или `embeddings`.

Основные коды ответа:

- **200** — запрос обработан.
- **400** — содержимое запроса не подходит правилам приложения, например пустой текст или неизвестный метод.
- **422** — тело запроса не проходит проверку типов/структуры Pydantic (например, обязательное поле `query` пропущено или `top_k` задан строкой, которую нельзя преобразовать в число).
- **503** — временно недоступен нужный ресурс, например документы или embedding-модель.

При импорте API embedding-модель не скачивается. Функция `get_embeddings` импортирует и создаёт модель только при первом embeddings-запросе, что позволяет использовать TF-IDF без неё.

## 7. Тестирование

Автоматические тесты проверяют ожидаемое поведение после изменений. `pytest` находит функции `test_...` в файлах `tests/` и сообщает о пройденных и упавших проверках. Запуск из корня проекта:

```bash
python -m pytest
```

Тесты охватывают загрузку и chunking (в том числе форматирование кода и ограничения токенов), поиск, API и поведение HTTP-клиента Ollama.

**Mock** — подмена зависимости тестовым объектом или ответом. Например, тест Ollama может подменить HTTP-ответ и проверить, как код его разбирает, без работающего сервера. Это проверяет интеграционный код на уровне клиента, но не доказывает, что настоящая Qwen запущена, доступна и генерирует качественные ответы. Для настоящей проверки требуется отдельно запустить Ollama и скачать модель.

## 8. Эксперименты и метрики

**Hit@1** — доля вопросов, для которых ожидаемый документ занимает первое место. **Hit@3** — доля вопросов, где ожидаемый документ входит в первые три результата.

Оценка по фрагментам может засчитать несколько верхних мест одному исходному документу. Проект дополнительно проходит выдачу по рангу и считает только первое появление каждого уникального источника. Так измеряется, попал ли нужный документ в top-k, а не сколько его фрагментов заняли выдачу.

В эксперименте всего 13 вопросов — слишком мало для серьёзных универсальных выводов. TF-IDF здесь конкурентоспособен, потому что запросы содержат характерные термины из небольшого корпуса и лексическое совпадение работает хорошо. Нельзя объявлять embeddings лучше только из-за сложности модели: сравнивать нужно измеряемый результат на подходящем тестовом наборе.

Есть ещё ограничение сравнения: TF-IDF использует окна по словам, embeddings — окна по токенизатору соответствующей модели. Поэтому результаты относятся к связке «разбиение + индекс + ранжирование», а не к изолированному сравнению алгоритмов. Скорость зависит от окружения. Сохранённые результаты отдельно учитывают среднее время запроса, загрузку модели и построение индекса. Среднее время запроса не включает загрузку модели и построение индекса.

По сохранённому эксперименту TF-IDF дал Hit@1 11/13 и Hit@3 13/13; `all-MiniLM-L6-v2` — 10/13 и 11/13; `paraphrase-multilingual-MiniLM-L12-v2` — 10/13 и 13/13. Подробные данные и версии зависимостей находятся в `results/retrieval_comparison.json`; повторный запуск — `python scripts/evaluate_retrieval.py`. Метрики retrieval оценивают поиск документов. Они не оценивают, насколько хорошо LLM сформулировала ответ.

## 9. Вопросы для собеседования

1. **Что такое RAG?** — Сначала ищем контекст в документах, затем передаём его языковой модели. *Проверяют понимание этапов системы.*
2. **Чем retrieval отличается от generation?** — Retrieval выбирает существующие данные; generation создаёт текст. *Проверяют, не смешиваются ли метрики поиска и ответа.*
3. **Зачем нужны chunks?** — Они позволяют сравнивать с запросом части документа, а не весь корпус целиком. *Проверяют понимание индексации.*
4. **Что такое overlap?** — Пересечение соседних фрагментов, сохраняющее контекст на границах. *Проверяют понимание chunking.*
5. **Почему нельзя считать токены словами?** — Токенизатор делит текст по правилам конкретной модели, не один токен на слово. *Проверяют понимание входного формата LLM.*
6. **Из чего состоит TF-IDF?** — Из частоты термина в тексте и обратной частоты документов. *Проверяют основы классического поиска.*
7. **Что делает IDF?** — Понижает вес распространённых слов и выделяет более информативные. *Проверяют понимание весов признаков.*
8. **Что означает cosine similarity?** — Сходство направлений двух векторов. *Проверяют базовую линейную алгебру для поиска.*
9. **Когда TF-IDF может быть лучше embeddings?** — Когда важны совпадения конкретных технических терминов и корпус небольшой. *Проверяют умение выбирать простое решение по данным.*
10. **Что такое embedding?** — Числовое представление текста, кодирующее полезные модели смысловые свойства. *Проверяют понимание семантического поиска.*
11. **Почему длинные chunks обрезались?** — Их токенизированная длина превышала контекстное ограничение модели. *Проверяют знание причины дефекта.*
12. **Почему tokenizer-aware chunking надёжнее?** — Он считает токены реальным токенизатором и учитывает специальные токены. *Проверяют понимание исправления.*
13. **Зачем лениво загружать embedding-модель?** — Чтобы импорт API и запросы TF-IDF не требовали загрузки модели. *Проверяют практические свойства запуска.*
14. **Что передаётся Ollama?** — Вопрос, инструкция и найденные текстовые отрывки в prompt. *Проверяют понимание интеграции.*
15. **Почему prompt с контекстом не гарантирует правду?** — LLM всё ещё может ошибиться при интерпретации или сгенерировать неподтверждённый вывод. *Проверяют понимание ограничений генерации.*
16. **Что проверяет mock-тест Ollama?** — Обработку запроса/ответа клиента без реального сервера и модели. *Проверяют качество тестовых выводов.*
17. **Что такое Hit@3?** — Доля запросов, где ожидаемый документ есть среди первых трёх уникальных документов. *Проверяют чтение метрики.*
18. **Почему 13 запросов недостаточно?** — Результат сильно зависит от состава небольшой выборки и не обобщается на другие запросы. *Проверяют критическое отношение к экспериментам.*

## 10. Практические задания

1. Вызови TF-IDF-поиск с `top_k=1`, затем с `top_k=5`; сравни количество и порядок результатов.
2. Добавь небольшой тематический `.txt` в соответствующий каталог `data/` и проверь, что `load_documents` его обнаруживает.
3. Подбери запрос, который возвращает неожиданный результат; объясни его по словам в запросе и тексту результата.
4. Добавь тест, проверяющий, что пустой запрос к поисковому классу возвращает пустой список.
5. Измени один контрольный вопрос и ожидаемый файл в `data/evaluation_queries.json`; запусти `python scripts/evaluate_retrieval.py` и сравни метрики. Зафиксируй изменение состава набора.
6. Добавь простую метрику времени для TF-IDF поиска, не включая построение индекса, и опиши методику измерения.
7. Проверь API-запрос с неизвестным методом и добавь тест для кода ответа и безопасного текста ошибки.
